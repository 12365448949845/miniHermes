## 一、项目概述

MiniHermes 是一个 Python 写的 AI 编程助手 CLI，通过 OpenAI 兼容 API 接入多种 LLM，支持工具调用、记忆持久化、技能系统。

| 维度 | 说明 |
|------|------|
| 语言 | Python ≥3.11 |
| 打包 | hatchling, wheel |
| UI | prompt_toolkit 终端应用 |
| 配置 | `~/.minihermes/config.yaml`（首次运行引导生成） |
| 入口 | `python main.py` → `minihermes` CLI 命令 |

## 二、从启动到响应的完整调用链路

### 2.1 启动链路（main.py）

```
main()
  ├── config.load()                          # 读 ~/.minihermes/config.yaml
  │     └── 缺键则从 config/config.yaml 补齐 → 回写
  ├── SessionDB()                            # 打开 SQLite WAL
  │     └── 建表 + FTS5 索引 + schema 迁移
  ├── Provider()                             # 构建 OpenAI client（max_retries=0）
  ├── StreamRenderer()                       # 流式渲染器
  ├── AppState()                             # CLI/后台线程共享状态容器
  ├── Agent(provider, db, clarify_callback, approval_callback)
  │     ├── build_system_prompt()            # 多层组装 prompt
  │     │     ├── SOUL.md → MEMORY.md/USER.md 冻结快照
  │     │     ├── 上下文文件发现（minihermes.md 等）
  │     │     ├── Skills 索引
  │     │     └── env/平台提示
  │     ├── 计算固定开销 token 数
  │     └── ContextCompressor(provider)      # 读取压缩阈值配置
  ├── db.create_session()                    # 写入 sessions 表
  ├── sync_builtin_skills()                  # 同步内置技能到 ~/.minihermes/skills/
  ├── build_app(state)                       # 构建 prompt_toolkit Application
  ├── Thread(conversation_loop)              # daemon 线程消费输入
  └── app.run()                              # 主线程进入 UI 事件循环
```

### 2.2 单轮对话链路（用户输入到响应）

```
用户输入
    │
    ▼
┌─ 主线程: Keyboard 事件 → input_queue.put(user_input)
│
├─ Daemon 线程: conversation_loop()
│   │
│   ├── 斜杠命令检测 (/clear /exit /plan 等)
│   │     └── 命中 → 处理 → continue
│   │
│   ├── Plan mode 检测 (__PLAN_MODE__: 前缀)
│   │     ├── 创建 plan_agent（只读工具、追加 PLAN_MODE_PROMPT）
│   │     ├── plan_agent.run_conversation() → 生成方案
│   │     ├── 写方案文件 → .minihermes/plans/<timestamp>.md
│   │     ├── 审批 UI → 用户选 execute/cancel
│   │     └── 若执行：将方案作为新 user input 重新进入 agent
│   │
│   ├── @file 引用预处理 (cli/context_ref.py)
│   │     ├── PATTERN 正则解析 @file:path:10-25
│   │     ├── 文件展开：二进制检测 → 行范围截取 → token 估算
│   │     └── 拼接到消息末尾，移除 @file token
│   │
│   ├── agent.run_conversation(user_message, history, renderer, session_id)
│   │   │
│   │   ├── 构建 messages = [system_prompt] + history + [user_msg]
│   │   ├── 写入 user 消息到 DB
│   │   │
│   │   ├── ── while 主循环（IterationBudget 控制上限）──
│   │   │   │
│   │   │   ├── 检查点 1: _estimate_tokens() → ContextCompressor.should_compress()
│   │   │   │     ├── 超过 threshold → 触发五阶段压缩
│   │   │   │     │   Phase 1: 边界确定 + tool pair 原子性保护
│   │   │   │     │   Phase 2: 大型工具输出裁剪
│   │   │   │     │   Phase 3: LLM 生成结构化摘要
│   │   │   │     │   Phase 4: Tool pair sanitization（修复孤立对）
│   │   │   │     │   Phase 5: 组装结果 + DB session 分裂
│   │   │   │     └── Anti-thrashing: 连续 2 次无效压缩→暂停
│   │   │   │
│   │   │   ├── provider.stream(messages, tools, callbacks)
│   │   │   │     ├── _sanitize_messages() → 剥离空 assistant、合并连续 user
│   │   │   │     ├── _stream_once() → OpenAI SDK stream
│   │   │   │     │     ├── 逐 chunk 累加: content + reasoning + tool_calls(按index)
│   │   │   │     │     ├── on_delta → StreamRenderer 实时渲染
│   │   │   │     │     ├── on_thinking → 思考过程展示
│   │   │   │     │     ├── on_tool_start → 工具调用提示
│   │   │   │     │     ├── 诊断 malformed tool_calls → 落盘 ~/.minihermes/logs/
│   │   │   │     │     └── 返回 StreamResult
│   │   │   │     └── 错误时: classify_api_error() → jittered_backoff 重试
│   │   │   │
│   │   │   ├── 检查点 2: 真实 usage 更新 token 追踪
│   │   │   ├── 写入 assistant 消息到 DB
│   │   │   ├── 进化计数器 +1（skill_nudge 触发检查用）
│   │   │   │
│   │   │   ├── 无 tool_calls → final_response → break（退出循环）
│   │   │   │
│   │   │   └── 有 tool_calls → 逐一执行:
│   │   │         ├── JSON 解析（失败则回填错误让模型重发）
│   │   │         ├── 审批 gate:
│   │   │         │     bash → check_command() → block/confirm/allow
│   │   │         │     write_file → check_write_file() → confirm/allow
│   │   │         │         ├── block → BLOCKED 错误返回
│   │   │         │         ├── confirm → 弹出审批 UI → once/session/deny
│   │   │         │         └── allow → 直接执行
│   │   │         ├── 预读旧内容（write_file 前，用于 diff 渲染）
│   │   │         ├── _execute_tool() → tool_registry.execute()
│   │   │         │     └── execute_with_retry() (retry.py)
│   │   │         │           └── 超时/瞬态错误 → 自动重试（max_retries=2）
│   │   │         ├── 进化计数器重置（若为 memory/skill_manage 工具）
│   │   │         ├── inline diff 渲染（write_file 后）
│   │   │         └── 写入 tool 结果到 DB
│   │   │
│   │   └── 返回 ConversationResult(messages, session_id, compressed)
│   │
│   ├── /init 完成时: 若 minihermes.md 已生成 → 重建 system_prompt
│   ├── 状态栏更新: token 使用百分比条
│   ├── state.conversation_history = result.messages
│   ├── 压缩后 session 可能改变 → 更新 state.session_id
│   ├── _try_nudge() → 进化系统 nudge 触发检查
│   └── /clear 提示（每 20 轮）
│
└── 退出时: curator 维护 + db.end_session()
```

## 三、上下文工程深度剖析

这是 MiniHermes 最核心的设计模块，负责保证在长对话中 Agent 始终能看到"足够且正确"的上下文。

### 3.1 系统提示词（多层组装）

`prompt/builder.py` 的 `build_system_prompt()` 每次 session 启动调用一次，之后 session 内不变（保证前缀缓存命中）：

| 层级 | 内容 | 来源 | 作用 |
|------|------|------|------|
| Layer 1 | 身份 | SOUL.md（不存在则自动创建） | 定义 Agent 角色 |
| — | 工具行为引导 | 按已注册工具条件注入 | 指导 LLM 正确使用工具 |
| Layer 7 | 记忆快照 | MemoryStore._snapshot（冻结副本） | 跨 session 知识传递 |
| Layer 9 | 项目上下文 | minihermes.md → .hermes.md → AGENTS.md → CLAUDE.md | 项目背景 |
| — | Skills 索引 | discover_skills() 扫描全局+项目技能 | 告知可用技能 |
| Layer 10 | 时间戳 | 会话开始时间 + 模型名 | 时间感知 |
| Layer 10.5 | 环境事实块 | cwd + platform + OS + 日期 | 环境感知 |
| Layer 11 | 环境提示 | 动态检测 macOS/Linux/WSL/Windows | 行为适配 |
| Layer 12 | 平台提示 | CLI 固定指引（不用 markdown） | 输出格式 |

**设计要点：**

- **前缀缓存策略**：system_prompt 在 session 内不变。API 第二轮起可命中前缀缓存。仅 `/init` 命令完成后重建（注入新生成的 minihermes.md），会中断缓存。
- **条件注入**：工具行为引导按 `_REGISTRY` 中实际注册的工具名注入。新增工具后引导自动生效。
- **注入检测**：`_scan_for_injection()` 检测所有上下文文件中是否含注入威胁（不可见 Unicode、prompt override 关键字）。发现则 BLOCKED。
- **截断策略**：上下文文件超 20K chars 时，保留头 70% + 尾 20%。

### 3.2 记忆系统：双轨道 + 冻结快照

`tools/memory.py` 实现持久化记忆，是最核心的跨 session 知识传递机制。

**双轨道架构：**

```
~/.minihermes/memory/
├── MEMORY.md   — Agent 笔记（环境事实、项目约定、工具特性）上限 2200 chars
└── USER.md     — 用户画像（偏好、背景）上限 1375 chars
```

**冻结快照（Snapshot）模式：**

```
Session 启动
  ├── MemoryStore.load_from_disk()
  │     ├── 读 MEMORY.md / USER.md → memory_entries / user_entries
  │     └── 复制到 _snapshot（在此 session 内永不修改）
  ├── format_for_system_prompt() → 注入 system prompt
  │     ══ MEMORY (55%) ... ══
  │     ══ USER PROFILE (11%) ... ══
  └── 工具调用 memory 操作 → 修改 live entries → 写盘
        但 _snapshot 不变 → system prompt 不变 → 前缀缓存继续命中
        下次 session 启动时 load_from_disk() 重新捕获快照，更新生效
```

**为什么这样设计：**
1. system prompt 整个 session 内不变，前缀缓存持续命中
2. 写盘即持久，下次 session 自动生效
3. 容量控制（2200/1375 char 上限），防止记忆膨胀污染上下文
4. `---\n` 作为条目分隔符，简洁可读

### 3.3 上下文压缩：五阶段工程

`context/compressor.py` 的核心设计。

**触发机制（双检查点）：**

```
检查点 1（调 LLM 前）：
  estimate_tokens > threshold_tokens
  threshold_tokens = context_window × threshold_percent（默认 50%）

检查点 2（LLM 响应后）：
  真实 prompt_tokens 更新追踪，下次检查点 1 更精确
```

**五阶段流程：**

```
Phase 1: 边界确定
  HEAD: 保护前 protect_first_n（默认 2）条
  TAIL: 从末尾反向切 tail_ratio（默认 20%）条，保证 tool pair 原子性
        _align_boundary_backward(): 切在 tool result → 扩展到对应 assistant
        _ensure_last_user_in_tail(): 确保最后 user 在 TAIL
  MIDDLE: 剩余 → 待压缩

Phase 2: Tool output pruning
  tool content > 500 chars → 截断为 1-line: "[tool_name] ... (total_len chars omitted)"
  tool_call arguments > 500 chars → 截断

Phase 3: LLM 摘要生成 ★ 核心
  首次压缩: 12-section 结构化模板
    Primary Request / Goal / Constraints / Completed Actions / Active State
    In Progress / Blocked / Key Decisions / Relevant Files / Remaining Work
    Important User Messages / Critical Context
  迭代压缩: 检测到已有 summary → 保留旧摘要 + 追加新 turns
  summary_budget = middle_tokens × 20%, 上限 12000
  temperature=0.3, 非流式（节省成本）

Phase 4: Tool pair sanitization
  Case 1: 移除孤立 tool results（call_id 不在任何 assistant 中）
  Case 2: 为缺失 result 插入 stub

Phase 5: 组装 + session 分裂
  _determine_summary_role(): 确定 summary 的 role（避免相邻同 role）
  冲突时合并 summary 到 tail 第一条
  DB: 创建 child session（parent_session_id=原ID）
  原 session end_reason="compression"
  Anti-thrashing: 连续 2 次 token 节省 < 10% → 暂停压缩
```

**Anti-thrashing 设计：**
```
should_compress():
  ├── 未超 threshold → false
  ├── 在 cooldown 期（上次压缩失败后60s）→ false
  └── ineffective_count ≥ 2 → false（停止无意义压缩）
```

### 3.4 项目上下文发现链

优先级（首个匹配即生效，互斥）：

```
1. minihermes.md     — 从 cwd 向上搜索到 git root（/init 生成）
2. .hermes.md / HERMES.md  — 向上搜索到 git root
3. AGENTS.md / agents.md   — 仅 cwd
4. CLAUDE.md / claude.md   — 仅 cwd
5. .cursorrules / .cursor/rules/*.mdc — 仅 cwd
```

每个文件经过：注入检测 → 截断（20K chars） → 组装为 `# Project Context` 块。

### 3.5 @file 引用预处理

`cli/context_ref.py` 在消息进入 Agent 前解析：

```
用户: "看 @file:agent/agent.py:30-50 这个方法"
  ├── PATTERN: (?<!\w)@file:(路径)(:行范围)?
  ├── 二进制检测（前4KB含null→跳过）
  ├── 文件读取 + 行范围截取 + token 估算
  ├── 语言推断（.py→python, .go→go）
  └── 输出: "看这个方法\n\n--- Attached Context ---\n\n📄 @file:..."
```

## 四、工具系统设计

### 4.1 注册机制

```python
# tools/__init__.py
_REGISTRY: dict[str, dict] = {}

@register({
    "type": "function",
    "function": {"name": "bash", "description": "...", "parameters": {...}}
})
def bash(command: str, timeout: int = 30) -> str: ...
```

子模块在 `__init__.py` 末尾 import 触发注册。16 个工具覆盖：系统(bash/process)、文件(read_file/write_file/list_dir)、信息(web_search/web_extract)、代码执行(execute_code)、记忆(memory)、委派(delegate_task)、交互(clarify/todo)、会话(session_search)、技能(skill_view/skill_manage)、视觉(recognize_image/generate_image)。

### 4.2 审批系统

两层防线（`tools/approval.py`）：

**硬拦截（HARDLINE）** — 绝对不执行：
- `rm /`, `mkfs`, `dd of=/dev/`, fork bomb, `shutdown`, `kill -9 1`

**软拦截（DANGEROUS）** — 弹出审批 UI：
- `rm`, `chmod 777`, `git reset --hard`, `git push --force`, `curl | sh`, `sudo`, `DROP TABLE`
- 审批选项: Allow once / Allow for session / Deny

write_file 也有独立的敏感路径检查（.env / .ssh/ / /etc/ 等）和敏感内容检查（API_KEY/SECRET 嵌入）。

### 4.3 工具输出截断

全局 50,000 chars 截断（head 40% + tail 60%），防止工具输出污染上下文。各工具有独立的更严格的限制（如 write_file 8K chars、web_search 8K chars）。

## 五、Agent 对话循环

### 5.1 IterationBudget

防止无限循环：每轮 LLM 调用消耗一次预算，默认 30 次。Plan mode 子 Agent 可覆盖更高（50）。

### 5.2 Token 估算优化

```
首次: _fixed_overhead + sum(各消息 content/4)
后续: _last_prompt_tokens + 新增消息 token（增量计算）
```

### 5.3 中断处理

双路径：
- **早期中断**（Ctrl+C 在 LLM 响应前）：写入空 assistant 占位（finish_reason=interrupted_before_response），防止连续 user 消息
- **流式中中断**（Ctrl+C 期间）：interrupt_check 检测 → 关闭 response → 保留部分内容

### 5.4 JSONDecodeError 容错

LLM 输出半截 JSON 时（max_tokens 截断或流式中断）：

1. 打印诊断（tool名、finish_reason、长度、preview）
2. 构造错误 tool_result 回填: "JSONDecodeError: ..., please re-issue"
3. 模型看到错误后可重新发送完整 tool call

Provider 层也有对应诊断：检测 malformed tool_calls → 打印精细信息（字节长度、字面换行统计、控制字符统计）→ 落盘 `~/.minihermes/logs/malformed_tool_call_XXXX.json`。

## 六、Provider 层：LLM 通信

### 6.1 设计要点

- **显式关闭 SDK 重试**（max_retries=0）：由 stream() 统一管理，避免 N×M 请求倍增
- **流式累积**：content 字符串拼接 / reasoning 独立轨道 / tool_calls 按 index 增量累积
- **消息清理**：剥离空 assistant 占位 / 跳过连续重复 user / 只传 API 认可字段
- **多模型兼容**：通过 OpenAI 兼容 API 接入不同 provider，支持 reasoning mode

### 6.2 错误分类

```
RateLimitError → retryable
APITimeoutError/APIConnectionError → retryable
5xx → retryable
Auth/Permission/NotFound → permanent
BadRequestError:
  context_length_exceeded → context_overflow（不重试）
  其他 → permanent
httpx 网络错误 → retryable
```

重试策略：jittered exponential backoff，优先使用 Retry-After header，可被中断。

## 七、会话持久化与恢复

### 7.1 数据库设计

SQLite WAL 模式，三个核心结构：

- **sessions 表**: id, source, model, model_config, system_prompt, started_at, ended_at, end_reason, parent_session_id(压缩链), title
- **messages 表**: session_id(FK), role, content, tool_calls(JSON), tool_call_id, tool_name, token_count, finish_reason, msg_type
- **messages_fts**: FTS5 虚拟表，INSERT 触发器自动同步

### 7.2 Session 分裂（压缩链路）

```
session_A (500+ msgs) → 压缩 → end_reason="compression"
session_B → parent_session_id=session_A (新消息)
  → 再次压缩 → end_reason="compression"
session_C → parent_session_id=session_B
```

恢复时 `/resume` 通过 `resolve_resume_session_id()` 沿链路走到最新子 session。

## 八、自动进化系统

### 8.1 触发机制

两个独立计数器（`_try_nudge()` 中检查）：

```
Memory nudge:  每 10 轮用户对话 → 复盘记忆
  ← _turns_since_memory 累积 → memory 工具调用时归零

Skill nudge:   每 10 次 LLM API 调用 → 识别可复用模式
  ← _iters_since_skill 累积 → skill_manage 调用时归零
```

反弹保护：用户主动操作时计数器归零，防止刚操作完就又被触发。

### 8.2 Nudge Agent

在独立 daemon 线程运行，不阻塞用户：

- Memory nudge: prompt 要求分析对话识别持久化事实，仅 memory 工具
- Skill nudge: prompt 要求分析对话识别可复用模式，skill_manage/skill_view/read_file 工具

### 8.3 Curator（技能库维护）

会话结束时运行：
- Phase 1（确定性）：7天未使用→stale, 30天→archived
- Phase 2（LLM）：auto skills ≥ 5 个时尝试合并
- 冷却期：两次运行间隔 ≥ 7 天

## 九、Plan Mode（规划-审批-执行）

```
"/plan 创建 REST API"
  Phase 1: plan_agent（只读工具）→ 生成方案 → 保存 .minihermes/plans/
  Phase 2: 审批 UI → Execute this plan / Cancel
```

## 十、子 Agent 委派

`agent/delegate.py` 创建完全隔离的子 Agent：

- **上下文隔离**：固定简化的 `_CHILD_SYSTEM_PROMPT`（无记忆/技能/项目上下文）
- **工具限制**：始终禁用 delegate_task + clarify（防递归委派和反问）
- **无持久化**：db=None，不写 DB
- **auto_approve=True**：无需审批
- **max_iterations=15**：低于父的 30

同步阻塞执行，返回 DelegationResult，子 Agent 有独立缩进渲染器。

## 十一、多级重试体系

**三级重试：**

| 级别 | 位置 | 策略 |
|------|------|------|
| 工具执行 | retry.py | TIMEOUT → timeout×2 重试 / TRANSIENT → 重试 / PERMANENT → 不重试 |
| API 调用 | provider.py | classify_api_error → jittered_backoff + Retry-After 优先 |
| SDK 禁用 | Provider.__init__ | max_retries=0，防止 N×M 请求倍增 |

## 十三、设计哲学

### 核心原则

1. **简单优先**：组件自包含，避免框架依赖。每个包 < 10 个文件，核心类 < 500 行
2. **失败可观测**：JSON 解析错误落盘、工具重试日志、budget 警告——不求永不失败，求失败可追溯
3. **渐进式复杂度**：简单路径（纯文本回复）走快速通道，复杂路径（工具调用→审批→压缩→重试）走完整管线
4. **向前兼容**：配置模板合并，新功能自动获得默认值

### 与主流方案的设计对比

| 维度 | MiniHermes | Claude Code | Cursor | OpenCode |
|------|-----------|-------------|--------|----------|
| **语言** | Python | TypeScript | TypeScript | Python |
| **上下文压缩** | 5 阶段结构化压缩 | LLM 自动摘要 | 滑动窗口 + 摘要 | 增量摘要 |
| **记忆系统** | 双轨道 Markdown 文件 | 单文件 MEMORY.md | `.cursorrules` 文件 | 无内置 |
| **工具注册** | 装饰器 + 模块导入 | MCP 协议 | 内置 + 扩展 | 函数装饰器 |
| **审批机制** | 两层（硬拦截 + 软拦截 + session 白名单） | ask 模式 | 权限分级 | 无 |
| **子 Agent** | 独立上下文 + 受限工具 | TodoWrite + Agent 委派 | 无 | 无 |
| **会话持久化** | SQLite WAL + FTS5 | JSONL 文件 | SQLite | SQLite |
| **TUI 框架** | prompt_toolkit | Ink (React) | 自研 | Textual |

### MiniHermes 的独特价值

1. **Python 生态友好**：纯 Python 实现，适合 Python 开发者定制和扩展
2. **模型无关**：任何 OpenAI 兼容 API 可用，不绑定特定厂商
3. **内存轻量**：单进程运行，不依赖 Node.js、Docker 等外部运行时
4. **透明可控**：记忆、配置、会话均为可读文本文件，用户可直接编辑

---

## 十四、关键技术决策

1. **双线程 CLI**：主线程 UI 事件循环 + daemon 线程对话循环，Queue 解耦。参考 hermes-agent 的多线程模型
2. **冻结快照记忆**：MemoryStore 启动时冻结，保证 system prompt 前缀缓存稳定性。平衡了实时性与速度
3. **五阶段上下文压缩**：带边界保护、tool pair 原子性、anti-thrashing 的完整压缩管线。对比业界方案选择结构化压缩
4. **Anti-thrashing**：连续无效压缩 2 次即暂停，防止恶性循环。这是生产环境中发现的实际问题
5. **子 Agent 隔离**：独立上下文、受限工具、无 DB、auto_approve。参考 hermes 的 delegate 设计
6. **三级重试**：工具级 + API 级 + SDK 禁用，避免 N×M 倍增。SDK 默认重试 2 次，我们显式关闭后统一管理
7. **配置模板合并**：新功能自动兼容老用户。用户配置只存与默认不同的项
8. **@file 预处理**：在 Agent 循环外注入文件内容，不占用 LLM 工具调用预算
9. **工具行为引导条件注入**：按实际注册工具动态添加，避免对不存在工具的幻觉引导
10. **JSONDecodeError 容错 + malformed 诊断**：Agent 层回填 + Provider 层落盘，全面覆盖 LLM 输出异常
11. **进化双计数器 + 反弹保护**：memory/skill 独立计数，主动操作时归零
12. **中文注释为主**：降低国内开发者阅读门槛
